## タスク詳細

### T-08: 在庫データを永続化する（API 接続）

- **対象要件**: 要件定義書「6. データ要件」「9. 制約条件（データ消失なし）」
- **やること**:
  - `src/features/*/api/` のモック実装を、実際のデータソースに接続する
  - サーバー状態の管理に **TanStack Query を初めて実際に使う**（導入済み・未使用）。
    フィルタ条件は既に Zustand（`useInventoryFilterStore`）にあるので、この線引きを崩さない
  - 既存の `InventoryResponse`（snake_case）→ `Inventory`（camelCase）の変換層を実装する。
    型は定義済みだが変換が使われていない
  - **「登録日」をデータモデルに追加する**。要件定義書「6. データ要件」にある項目だが、
    現在の `Inventory` 型に存在しない（永続化して初めて意味を持つ項目のためここに含める）
- **完了条件**: ブラウザをリロードしても登録した在庫が残る。
  在庫の登録・編集・削除がすべて永続化される
- **備考**:
  - **接続先の方式が未決**（下の「確認したいこと」#1）。Go バックエンド接続か localStorage か
  - Go バックエンドは別リポジトリ（`../backend`）。API 契約は各設計書「7. API 仕様」に
    定義済みなので、それを Go 側の実装仕様として使える
  - カテゴリ・保管場所マスタ（`src/shared/api/`）も同じ方式に揃える必要がある

### T-09: 期限接近のプッシュ通知を配信する

- **対象要件**: 要件定義書「5-6. 消費期限管理・通知機能」
- **やること**:
  - Service Worker を登録し、Web Push の購読（通知許可のリクエストと購読情報の保存）を実装する
  - T-06 で作った通知設定（「◯日前」）を実際の配信条件として使う
  - 期限が近い在庫を検出してプッシュを送る処理を実装する
- **完了条件**: 設定した日数前になると、アプリを開いていなくても端末に通知が届く
- **備考**:
  - **5-6 のうち画面（通知タイミング設定）は T-06 で完了済み。配信の実体が未実装**
  - サーバーからの送信・VAPID 鍵の管理・HTTPS 配信が前提になるため、
    **バックエンドとホスティングが必要**（要件定義書「9. 制約条件」でインフラは未定）
  - 期限切れの警告表示（赤色）は T-01 で実装済み（`expiration.ts` の `expired` / `warning`）

## 確認したいこと（要件定義書に書かれておらず、勝手に決めない）

1. **T-08 の永続化方式**。次のどちらで進めるか。
   - **(a) Go バックエンド + PostgreSQL に接続する** … 要件定義書「9. 技術的制約」どおり。
     別リポジトリの実装が必要で重いが、本来の構成
   - **(b) 先に localStorage で永続化する** … フロントだけで完結し、すぐ日常利用を始められる。
     API 層の差し替えだけで後から (a) に移行できる
2. **ホスティング先**（要件定義書「9. 制約条件」で未定）。
   T-09 のプッシュ通知は HTTPS 環境が必須なので、遅くとも T-09 の設計前に決める必要がある。
