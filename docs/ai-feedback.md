# AI駆動開発フィードバックログ

`design-impl-reviewer` が出力した「ワークフロー改善提案」をここに蓄積する。

## 運用ルール

1. レビュー完了後、メインセッションが提案を**日付付きで下に追記**する（新しいものを上に）。
2. 提案は勝手に反映しない。溜まった段階でユーザーに提示し、**承認を得てから**
   `CLAUDE.md` / `docs/coding-standards.md` / `.claude/skills/*` / `.claude/agents/*` へ反映する。
3. 反映したら該当エントリのステータスを「反映済み」に更新し、反映先を記録する。
   却下した場合は「却下」とその理由を残す（同じ提案が繰り返し出るのを防ぐため）。

## 記録フォーマット

```markdown
### YYYY-MM-DD / <対象機能名>

| --- | -------- | ---------- | ---------- | ---------- |
| 1   |          |            |            | 未対応     |

**詳細**
（提案の背景と、具体的な追記文案）
```

ステータス: `未対応` / `反映済み（反映先）` / `却下（理由）` / `保留`

**詳細**

**#1 — `pnpm build` によるレンダリング種別の確認**

`today = new Date()` をコンポーネントの既定値にする設計判断自体は妥当だが、
App Router では「動的 API を使わないページは静的化される」ため、ビルド時刻が HTML に焼き込まれる。
lint / typecheck / test はいずれもこれを検出できず、`pnpm build` の Route 一覧で初めて気づけた。
今回の実装では `export const dynamic = 'force-dynamic'` で是正済み。

2026-08-06 反映（ユーザー承認済み）。検証側（`CLAUDE.md` / `implement-from-design`）に
`pnpm build` での Route 一覧確認を追加したのに加え、設計側でも同じ抜けが起きないよう
`docs/design/_template.md`「6. 状態管理・データフロー」に**レンダリング戦略**の項目を追加した。

**#2 — 設計書が規約の例外を認める場合の扱い（保留）**

今回は設計書で `formatDate` のテストを `expiration.test.ts` に同居させる例外を認めたが、
レビューで「実装ファイルに対応するテストが無い」と判定された。
**是正として例外自体を取りやめ、規約どおり `formatDate.test.ts` を分離した**ため、
現時点でルール追加の実需はない。同種の例外が再び必要になった段階で判断する。

**#3 — 見出しレベルの設計項目**

設計書の UI 要素表に「見出し」とだけ書かれ HTML レベルの指定が無かったため、
実装が `<h2>` 始まりとなりページに `<h1>` が存在しない状態になった（WCAG 2.4.6）。
今回は `<h1>`（在庫一覧）→ `<h2>`（保管場所名）に是正済み。

2026-08-06 反映（ユーザー承認済み）。テンプレートの「3. 画面・UI 仕様」に
「見出しテキスト / レベル / 備考」の表を必須項目として追加した。

**#4 — モックデータの日付**

絶対日付をハードコードすると、日が経つにつれて
「期限切れ・期限間近・余裕あり・期限なし」の4パターンが崩れ、動作確認に使えなくなる。
今回は当日からの相対（`shiftDays(-2)` など）で生成するよう是正済み。

2026-08-06 反映（ユーザー承認済み）。テンプレートの「7. API 仕様 / 現段階のモック実装」に
相対日付の指針と、モックが再現すべき状態パターンを列挙する項目を追加した。
