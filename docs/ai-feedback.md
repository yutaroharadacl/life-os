# AI駆動開発フィードバックログ

`design-impl-reviewer` が出力した「ワークフロー改善提案」をここに蓄積する。

## 運用ルール

1. レビュー完了後、メインセッションが提案を**日付付きで下に追記**する（新しいものを上に）。
2. 提案は勝手に反映しない。**`未対応` / `保留` の提案が合計3件以上溜まったら**、
   次に `/create-pr` を実行するタイミングでユーザーに一括レビューを提案する
   （`.claude/skills/create-pr/SKILL.md`「0. レビュー通過を確認する」で機械的にカウントする）。
   3件未満でも、ユーザーから明示的に要求があれば随時レビューしてよい。
   提示後は**承認を得てから** `CLAUDE.md` / `docs/coding-standards.md` / `.claude/skills/*` /
   `.claude/agents/*` へ反映する。
3. 反映したら該当エントリのステータスを「反映済み」に更新し、反映先を記録する。
   却下した場合は「却下」とその理由を残す（同じ提案が繰り返し出るのを防ぐため）。
4. **一括レビューの際は、追加する提案だけでなく「もう不要になった足場」も必ず一度は問う。**
   ハーネスの各ルール・検査・手順は「モデルが単独ではできない」という**仮説**であり、
   モデルの能力向上とともに陳腐化する。この運用は放っておくと追加方向にしか動かないため、
   一括レビューを**剪定を検討する唯一の機会**として明示的に組み込む。
   検討したら結論（削除した／残す判断とその理由）を必ずログに残す。何も削らなかった場合も
   「今回は剪定なし」と記録する（検討したこと自体を可視化し、次回の判断材料にするため）。

## 記録フォーマット

```markdown
### YYYY-MM-DD / <対象機能名>

| #   | 提案内容 | 逸脱の原因 | 反映先候補 | ステータス |
| --- | -------- | ---------- | ---------- | ---------- |
| 1   |          |            |            | 未対応     |

**詳細**
（提案の背景と、具体的な追記文案）
```

ステータス: `未対応` / `反映済み（反映先）` / `却下（理由）` / `保留`

### 2026-08-21 / 未対応バックログの一括適用

対象: ユーザー提起「未対応を適用して」。この時点で残っていた `未対応` 5件をすべて反映した。
各項目のステータスは該当エントリ側で「反映済み」に更新済み。

| 適用した項目 | 出典 | 主な成果物 |
| ------------ | ---- | ---------- |
| テストカバレッジの機械検査 | 2026-08-20 #1 | `scripts/check-test-coverage.mjs`、`pnpm check:tests` |
| 重要度の較正 | 2026-08-21（動的検証）#2 | `docs/review-severity.md`（新設） |
| 到達不能な境界チェックの削除 | 2026-08-21（剪定監査）#5 | `design-impl-reviewer`、`code-reviewer` |
| Stop フックの条件付き化 | 同 #6 | `.claude/settings.json` |
| boundaries プラグインの移行 | 同 #7 | `eslint.config.mjs`、`CLAUDE.md` |

**適用中に判明したこと**

**1. boundaries の移行は2世代ぶんだった**

警告は v5→v6 の移行ガイドを案内していたが、実際に必要だったのは3点の同時変更だった。
段階的に適用して都度実測しないと気付けなかった。

- ルール名 `boundaries/element-types` → `boundaries/dependencies`（v7 で正式に deprecated）
- `rules` オプション → `policies`（v6→v7）
- セレクタを `{ element: { type: '…' } }` でラップ（v6→v7。`{ type: '…' }` だけでは警告が消えない）

強制レイヤーの中核のため、移行後に**5パターンすべてを実測**して挙動が移行前と同一であることを
確認した（app→feature 許可 / feature→同一 feature 許可 / feature→別 feature 禁止 /
feature→shared 許可 / shared→feature 禁止）。
途中、`rules` が無視されていた段階では app→feature が誤って禁止になっており、
実測していなければ**境界ルールが壊れたまま気付かなかった**。

**2. 重要度の較正は「複製」ではなく「単一の情報源」にした**

当初の提案は両エージェントへの追記だったが、それでは2つのルーブリックが drift し、
「判定ドリフトを防ぐ」という目的そのものを損なう。
`docs/review-severity.md` を新設し、両エージェントの「最初に読むもの」から参照させた。
`implement-from-design`「⑤ 自動レビュー」のゲート判定もこの基準に従う。

**3. Stop フックはフェイルセーフに倒した**

`git status --porcelain -- src` が空ならスキップする条件を付けた。
git が使えない状況では `|| echo force` により**実行する側**に倒れる。
検査を止める方向のミスが起きないようにするため。

### 2026-08-21 / 剪定監査（運用ルール4の初回実行）

対象: ユーザー提起「不要なハーネスはないか」。本日新設した運用ルール4（剪定）の初回適用。
判断はすべて実測（`npx eslint` の終了コード、grep による重複箇所の計数）に基づく。

**最重要の発見: 剪定の前提そのものが誤っていた**

`CLAUDE.md` は `any` と `console.log` を「いずれも ESLint エラー」と記載していたが、実測すると
`no-console` は `warn` で、**`pnpm lint` は終了コード0で通過していた**（`no-explicit-any` のみ error）。
この記述を信じて「lint が守るからプロンプト側は不要」と剪定していたら、
`console.log` は完全に無防備になっていた。
**剪定の前に「本当に下の層が守っているか」を実測すること**が教訓。

**詳細**

**#1 — 格上げの安全性確認**

`src/` 配下に `console.` の使用が1件も無いことを確認したうえで `error` に格上げした。
格上げ後、`console.log` は exit 1 で停止、`console.warn` / `console.error` は許可のまま、
`pnpm lint` / `typecheck` / `test` はすべて緑であることを確認済み。
この格上げにより `CLAUDE.md` の「いずれも ESLint エラー」という記述が**事実になった**ため、
同ファイルの修正は不要となった。

**#4 — 残した記述との線引き**

`console.log` / `any` の言及は5箇所あったが、機械的に全部消したのではなく次の基準で切り分けた。

- **lint より後に走るもの（2レビュアー）** → 到達不能なので削除。
  「探さないこと」と理由を明記し、再追加を防ぐ
- **lint より前に走るもの（`implement-from-design` の生成、`unit-test-writer`）** → **残す。**
  ここでの注意喚起には lint→修正の往復を1回減らす予防効果があり、重複ではない
- **常時コンテキストに載る `CLAUDE.md`** → 残す（開かないと読めない規約とはアクセスコストが違う）

**削らないと判断したもの（正当な重複）**

- `CLAUDE.md` の規約再掲 — 常時ロードされる／開かないと読めない、というアクセスコストの差が実質的
- 3つの停止ゲート — 入口がそれぞれ違う（設計後・実装後・PR前）
- `pnpm check:design` の3箇所（実装スキル「④ 検証」／`create-pr`／`pre-push`）—
  3回再発した逸脱に対する多層防御で、それぞれ入口が違う。#2 #3 の削除で計9箇所→7箇所に減った
- `unit-test-writer` — 能力の補完ではなく「実装ファイルを作れない」という TDD 順序の構造的保証。
  モデルが賢くなっても代替されない
- 1回だけ起きた逸脱への文章注意喚起 — ハーネス自身のルールが1回目は文章を許容している

**詳細**

**#1 — 増やす経路はあるが減らす経路が無い（反映済み）**

参考記事のアンチパターン「不要な複雑さの残存」「モデル進化を無視した固定ハーネス構成」に該当。
同趣旨は Anthropic の
[harnessing-claudes-intelligence](https://claude.com/blog/harnessing-claudes-intelligence)
でも *"what can I stop doing?"* として述べられており、確認した3記事すべてが同じ原則を挙げている。
`CLAUDE.md` の168→93行削減（2026-08-19）は重複整理であって、
「モデルが賢くなったから不要」という理由での剪定ではなかった。
一括レビューを剪定の唯一の機会として制度化し、`design-impl-reviewer` 側にも
削除提案（「削除:」と前置き）を出す権限を与えた。

**#2 — handoff（反映済み）**

参考記事は失敗モードの筆頭に「コンテキスト肥大化 → 初期指示の忘却 → 途中放棄」を挙げ、
実践ステップの1番目に「まずコンテキストリセット導入」を置いている。
本プロジェクトのタスク粒度は「1タスク=1設計書=1PR」（記事の分類で 30分〜1時間クラス）のため
緊急性は低いが、新規ファイル3つ以上の実装では設計書ステータス欄に
`実装中（②GREEN まで完了 / YYYY-MM-DD）` の形式で進捗を残すことにした。
`pnpm check:design` が `実装済み|レビュー済み` 以外を失敗扱いするため、
この書式のまま PR に進めない安全網が既存の検査でそのまま効く。
再開時は記録を鵜呑みにせず `git diff` / `pnpm test` で実態と照合する手順もあわせて明記した。

**#3 — タスク難度別の分岐（反映済み）**

参考記事の「10分以内＝ハーネスなし」「既知タスク＝簡略化」に対応。
「設計書を書くかどうか」の判断基準のみを緩め、**書いた場合の承認ゲートには手を入れていない**
（承認ゲートは 2026-08-06 のフィードバックに由来する別個のルールのため）。
省略する場合は宣言してユーザーの了解を得ること、省略時も `code-reviewer` は実施することを条件にした。

**詳細**

**#1 — 静的レビューから動的検証へ（反映済み）**

参考記事は、生成物を評価する際に「静的にコードを読む」だけでなく「実際に動かして検証する」
（Playwright MCP でページを実操作）ことの重要性を指摘している。このプロジェクトの自動レビューは
これまで読み取りコマンドのみで完結しており、画面操作の確認はメインセッションの自己申告任せだった。
過去に静的レビューだけで「メニューの背景クリックで閉じる」という設計書の1行の未実装を見落とした
前例がある（2026-08-18 #3）。`design-impl-reviewer` に `mcp__Claude_Browser__*` 系ツールを追加し、
UI/フロントエンド変更時は `.claude/launch.json` の `next-dev` を起動して「操作と遷移」表を1行ずつ
実操作で突き合わせる節を新設した。画面操作を伴わない差分（API・ロジックのみ）はスキップしてよい
としている。

**#2 — 重要度較正（当日中に反映済み）**

同記事は評価基準に few-shot 例を添えて較正しないとスコアがドリフトすると指摘しており、
本プロジェクトの「重要度: 高/中/低」判定にも同じリスクがある。
起票時点ではユーザー判断で見送ったが、同日の「未対応バックログの一括適用」で反映した。
反映先は当初案の「両エージェントへの追記」ではなく、単一の情報源
`docs/review-severity.md` の新設に変更している（複製すると drift し、目的を損なうため）。

**詳細**

**#1 — `useActionState` を使うテストの待ち方**

`InventoryForm` を `FormEvent` + `event.preventDefault()` から React 19 の
`<form action={submitAction}>` + `useActionState` に置き換えた際、送信ボタンを押した
直後に同期的に `expect` するテストが複数残った。`InventoryFormModal.test.tsx` の
「閉じる」テストなど一部は経験的に `waitFor` を使っていたが、`InventoryListsView.test.tsx`
の登録後アサーション（一覧反映・完了メッセージ・件数など）と `InventoryForm.test.tsx` の
`onSubmit` 呼び出し検証は同期的なままで、`pnpm test` をフルスイートで12回連続実行すると
2回失敗することを確認した。すべて `await screen.findByText(...)` / `await waitFor(...)` に
是正済み（是正後は12回連続成功を確認）。

2026-08-06 反映（ユーザー承認済み）。`docs/coding-standards.md`「何をテストするか」に
`useActionState` / `<form action>` 特有の待ち方の指針を追加した。

**#2 — 設計書のテスト観点チェックリストへの反映漏れ**

コードレビューで `createInventory` に `crypto.randomUUID` 非対応環境向けのフォールバックを
追加した際、設計書「7. API仕様」の本文には理由を追記したが、「9. テスト観点」の
チェックリストには反映し忘れていた（実装済みのテストとの乖離）。

2026-08-06 反映（ユーザー承認済み）。`docs/design/inventory-registration.md`
「9. テスト観点」の `createInventory(draft)` に異常系2件を追記した。

**詳細**

**#1 — `pnpm build` によるレンダリング種別の確認**

`today = new Date()` をコンポーネントの既定値にする設計判断自体は妥当だが、
App Router では「動的 API を使わないページは静的化される」ため、ビルド時刻が HTML に焼き込まれる。
lint / typecheck / test はいずれもこれを検出できず、`pnpm build` の Route 一覧で初めて気づけた。
今回の実装では `export const dynamic = 'force-dynamic'` で是正済み。

2026-08-06 反映（ユーザー承認済み）。検証側（`CLAUDE.md` / `implement-from-design`）に
`pnpm build` での Route 一覧確認を追加したのに加え、設計側でも同じ抜けが起きないよう
`docs/design/_template.md`「6. 状態管理・データフロー」に**レンダリング戦略**の項目を追加した。

**#2 — 設計書が規約の例外を認める場合の扱い（保留）**

今回は設計書で `formatDate` のテストを `expiration.test.ts` に同居させる例外を認めたが、
レビューで「実装ファイルに対応するテストが無い」と判定された。
**是正として例外自体を取りやめ、規約どおり `formatDate.test.ts` を分離した**ため、
現時点でルール追加の実需はない。同種の例外が再び必要になった段階で判断する。

**#3 — 見出しレベルの設計項目**

設計書の UI 要素表に「見出し」とだけ書かれ HTML レベルの指定が無かったため、
実装が `<h2>` 始まりとなりページに `<h1>` が存在しない状態になった（WCAG 2.4.6）。
今回は `<h1>`（在庫一覧）→ `<h2>`（保管場所名）に是正済み。

2026-08-06 反映（ユーザー承認済み）。テンプレートの「3. 画面・UI 仕様」に
「見出しテキスト / レベル / 備考」の表を必須項目として追加した。

**#4 — モックデータの日付**

絶対日付をハードコードすると、日が経つにつれて
「期限切れ・期限間近・余裕あり・期限なし」の4パターンが崩れ、動作確認に使えなくなる。
今回は当日からの相対（`shiftDays(-2)` など）で生成するよう是正済み。

2026-08-06 反映（ユーザー承認済み）。テンプレートの「7. API 仕様 / 現段階のモック実装」に
相対日付の指針と、モックが再現すべき状態パターンを列挙する項目を追加した。
