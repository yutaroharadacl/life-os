# レビュー指摘の重要度基準

`design-impl-reviewer` と `code-reviewer` が指摘に付ける「重要度」の唯一の基準。
**両エージェントはこのファイルを読んでから判定する。**

この基準が必要な理由: 重要度「高」が1件でもあれば実装フローは停止し、`/create-pr` にも進めない
（`CLAUDE.md`「3つの停止ゲート」）。2つのエージェントが別々の物差しで「高」を付けると、
ゲートの厳しさがレビューのたびに変わってしまう。

---

## 迷ったときの決め手

> **ユーザーがこの状態のアプリを触って気づくか。**
>
> - 気づく → **高**
> - 気づかないが、次に触る実装者が困る → **中**
> - どちらでもない → **低**

この問いで割り切れない場合のみ、下の分類を使う。

---

## 高 — ユーザーに見える壊れ、またはデータの誤り

1件でもあれば**フローを止める**。以下のいずれかに当たるもの。

- 設計書「3. 画面・UI 仕様」の表に明記された機能・操作・状態が**実装されていない**
- 期限・日付計算の誤り（本プロジェクトの中核機能のため、常に高）
- ユーザーの入力が失われる／保存されない／消える
- 実行時エラーやクラッシュ（`null` / `undefined` 参照、未定義プロパティへのアクセス）
- セキュリティ（XSS、機密情報のクライアントへの露出やログ出力）
- 要件定義書の要求を満たしていない

**例**: 設計書の「操作と遷移」表に「メニューの背景クリックで閉じる」とあるのに未実装
（`docs/ai-feedback.md` 2026-08-18 #3）→ **高**。ユーザーが操作して気づくため。

## 中 — 動くが、設計・規約から外れている

放置すると後段のコストになるもの。**フローは止めない**が、PR 前に対応を検討する。

- 型定義の項目名・型・必須性が設計書と違う
- 設計書「9. テスト観点」にある観点が**テストコードに落ちていない**
- コンポーネントの責務が設計書の記述と違う
- 設計書に無いファイルが増えている（＝設計書の更新漏れ、またはスコープ逸脱）
- 到達不能なコード、どこからも参照されない型やエクスポート
- 境界値（0件・空配列・`null`）のテストが無い

**例**: 設計書の型が `quantity: number` なのに実装が `string` → **中**。
画面上は動いてしまうが、Go バックエンド接続時に破綻する。

## 低 — 動作にも設計整合にも影響しない

- 命名の一貫性（規約違反ではないが揃っていない）
- 軽微な重複（2箇所程度。3箇所以上は中）
- コメント・JSDoc の不足
- より簡潔に書ける箇所

**例**: 同じ日付整形ロジックが2箇所にある → **低**。3箇所目が出たら中に上げる。

---

## 重要度を付けてはいけないもの

次は**そもそも指摘しない**（重要度の議論以前の問題）。

- **好みの問題** — 規約・設計書・要件のいずれにも根拠が無いもの
- **lint が機械的に止めるもの** — `any`、`console.log`、アーキテクチャ境界違反。
  両エージェントは `pnpm lint` 通過後にしか起動されないため、これらは到達不能
  （`docs/ai-feedback.md` 2026-08-21 の剪定監査）
- **推測** — `ファイル:行` の根拠を示せないもの
