# プロンプト → 詳細設計

実装に入る前に、`docs/design/_template.md` に沿った詳細設計書を作成する。

**このスキルではコードを書かない。** 設計書を作るところまでが担当。

## 手順

### 1. インプットを読む

必ずこの順で読む:

1. `docs/要件定義書_食料品在庫管理システム.md` の**該当章**（ユーザーの依頼がどの要件に対応するか特定する）
2. `docs/coding-standards.md`（設計を規約に適合させるため）
3. `docs/design/_template.md`（出力フォーマット）
4. `docs/tasks.md`（あれば。タスクIDが指定された場合はその詳細）

### 2. 既存コードを調査する

**新しく作る前に、再利用できるものを探す。** これを飛ばさない。

- `src/features/` 配下の既存コンポーネント・型・ユーティリティ
- 似た画面・似たデータ構造が既にないか
- 既存の型（`src/features/inventory/types/index.ts` など）を拡張すれば済まないか

調査結果は設計書の「5. コンポーネント設計」に反映し、
**再利用するもの／新規作成するものを明確に区別**する。

### 3. 設計する

`docs/design/_template.md` の**全10セクションを埋める**。特に重要なのは:

- **4. データ・型定義**: 実装時にそのままコピーできる粒度の TypeScript を書く
- **5. コンポーネント設計**: 作成・変更するファイルをパス単位で列挙する。
  アーキテクチャ境界（`app → feature → shared`）に違反しないこと
- **9. テスト観点**: `unit-test-writer` の入力になる。
  「入力 → 期待される結果」が読み取れる粒度で、正常系・異常系・境界値を具体的に書く

### 4. 未決事項は勝手に決めない（最重要）

仕様が要件定義書から読み取れない、または複数の解釈がある点は、
**推測で埋めずに「10. 未決事項・確認事項」に列挙する。**

例:

- 数量の単位はどう扱うか（個 / g / ml）
- 期限切れの在庫を一覧から自動で消すのか、警告色で残すのか
- 削除は物理削除か論理削除か

設計書を書き終えたら、未決事項を**ユーザーに提示して確認を取る**。
回答を得たら設計書に反映し、未決事項リストから消す。

### 5. 出力する

- 出力先: `docs/design/<機能名>.md`
- 機能名は**ケバブケースの英語**（例: `inventory-registration.md`, `category-master.md`）
- `docs/tasks.md` があれば、該当タスクの「状態」を `設計済み` に更新し、設計書へのリンクを張る

## 完了後

### 設計書の承認を得る（実装に入る前の必須ゲート）

> **未決事項が解決しても、そのまま実装に進んではならない。**
> ユーザーが設計書を読んでレビューする時間を確保するため、必ずここで一度止まる。

1. 設計書へのリンクと、**設計の要点**（スコープ、主要な設計判断、既存コードへの影響、
   特に削除・作り直しになるファイル）を短くまとめて提示する
2. 「この設計で実装を進めてよいか」を明示的に問い、**承認の返答を待つ**
3. 修正の指示があれば設計書を直し、再度承認を求める

承認を得てから `/implement-from-design docs/design/<機能名>.md` で実装に進む。

**「実装を開始します」のような依頼で始まった場合も、このゲートは省略しない。**
設計は実装の前提であり、前提が誤ったまま実装するとやり直しの範囲が大きくなるため。

## 注意

- Go バックエンドと PostgreSQL は**未着手**。API 仕様は将来の契約として定義しつつ、
  現段階の実装はモックである旨を「7. API 仕様」に明記する
- 要件定義書を書き換えない。要件の不備を見つけたら未決事項として報告する
- 設計書はレビューエージェントとの契約でもある。セクションを削らない
