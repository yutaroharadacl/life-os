# 要件 → タスク分割

要件定義書を「1タスク = 1詳細設計書 = 1PR」の粒度に分解し、`docs/tasks.md` にまとめる。

## 手順

### 1. 入力を確認する

- 対象範囲がユーザーから指定されていればそれに従う（例:「5-2 カテゴリマスタだけ」）
- 指定がなければ `docs/要件定義書_食料品在庫管理システム.md` の**フェーズ1スコープ全体**を対象にする
- フェーズ2（レシート読取・バーコード・家族共有・アカウント管理）は**対象外**。タスク化しない

### 2. 現状を把握する

- `docs/tasks.md` が既にあれば読む（**全面上書きせず差分追記する**）
- `src/features/` 配下の既存実装を確認し、着手済み・完了済みのものを把握する
- `docs/design/` にある既存の設計書を確認する

### 3. タスクに分解する

粒度の目安:

- **大きすぎ**: 「在庫管理機能を作る」← 設計書1枚に収まらない
- **小さすぎ**: 「Inventory 型に memo を追加する」← 単独で PR にする意味がない
- **ちょうどいい**: 「カテゴリマスタの一覧・追加・編集・削除画面」「在庫登録フォーム」

各タスクに以下を付ける:

- **ID**: `T-01` から連番
- **タスク名**: 動詞で終わる日本語（例:「在庫登録フォームを実装する」）
- **対象要件**: 要件定義書の章番号（例: `5-1`, `8-2`）
- **依存**: 先に完了している必要があるタスクの ID
- **状態**: `未着手` / `設計済み` / `実装中` / `完了`

### 4. 実装順を決める

依存関係を解決し、推奨する実装順を示す。判断基準:

- 型定義・共通コンポーネントなど、他タスクの土台になるものを先に
- 画面の骨格 → データ操作 → 通知など付随機能、の順
- 早くユーザーが動かして確認できるものを優先

### 5. 出力する

`docs/tasks.md` に以下の形式で書く。

```markdown
# 実装タスク一覧

最終更新: YYYY-MM-DD

## 推奨実装順

1. T-01 → 2. T-02 → ...

## タスク

| ID   | タスク名 | 対象要件 | 依存 | 状態   | 設計書 |
| ---- | -------- | -------- | ---- | ------ | ------ |
| T-01 |          | 5-1      | -    | 未着手 | -      |

## タスク詳細

### T-01: <タスク名>

- **対象要件**: 要件定義書「5-1. 在庫登録機能」
- **やること**: （2〜4行）
- **完了条件**: （何ができたら完了か）
- **備考**: （懸念・前提）
```

## 注意

- 要件定義書に書かれていない機能を勝手に足さない。必要だと思ったら「提案」として別枠で示し、ユーザーに確認する
- 要件定義書自体を書き換えない
- Go バックエンドと PostgreSQL は未着手のため、フロントエンドのタスクはモックデータ前提で分解する。
  バックエンドが必要なタスクはその旨を「備考」に明記する
- 完了後、次のステップとして `/detail-design` でタスクを1つ選んで設計に進むことを案内する
