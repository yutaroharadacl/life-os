# 詳細設計 → 実装（TDD 必須）

## 絶対に守るルール

> **テストファイルが存在しない状態で、実装ファイルを作成・編集してはならない。**

必ず「失敗するテストを書く → 実装で通す」の順で進める。
ユーザーが明示的に「テストは不要」と言った場合のみ例外とし、その場合はその旨を宣言してから進める。

## 手順

### 0. インプットを読む

1. 対象の `docs/design/<機能名>.md`
2. `docs/coding-standards.md`
3. `CLAUDE.md`

### 1. 事前チェック

次の2つを満たしていなければ実装に入らない。

1. 設計書の「10. 未決事項・確認事項」に**未解決の項目が残っていないこと。**
   残っていればユーザーに提示して確認を取り、設計書を更新してから進む
2. **設計書そのものについてユーザーの承認を得ていること。**
   同じ会話で `detail-design` から続けて来た場合も、承認の返答が無ければここで止まり、
   設計の要点を提示して「この設計で進めてよいか」を確認する

### 2. ① RED — 失敗するテストを先に書く

`unit-test-writer` サブエージェントを **RED モード**で起動する。渡す情報:

- 設計書のパス
- 設計書の「9. テスト観点」「4. データ・型定義」「5. コンポーネント設計」の内容
- **まだ実装は存在しないこと**、テストのみを書くこと
- 実装ファイルは作らないこと

エージェント完了後、自分で `pnpm test` を実行して確認する:

- テストファイルが作成されていること
- **テストが期待どおり失敗していること**（モジュール解決エラー、またはアサーション失敗）
- テストが通ってしまう場合 → そのテストは何も検証していない可能性が高い。
  内容を確認し、必要なら書き直しを指示する

### 3. ② GREEN — テストを通す実装

設計書の「5. コンポーネント設計」に列挙されたファイルを、記載された責務どおりに実装する。

- **設計書に無いファイルを勝手に増やさない。** 必要になったら**設計書を先に更新**し、その旨を報告する
- `docs/coding-standards.md` の構成（3点セット、バレル経由の参照、`type Props`、`@/` エイリアス）に従う
- アーキテクチャ境界を守る（`feature` から他の `feature` を import しない）
- `pnpm test` が緑になるまで実装する

**禁止**: テストを通すためにテスト側を書き換える（アサーションを弱める、`skip` する、削除する）。
仕様どおり実装してもテストが通らない場合は、**実装を止めて「仕様とテストのどちらが誤っているか」を報告**する。

### 4. ③ REFACTOR

テストが緑のまま、規約に沿って整理する。

- 重複の除去、命名の見直し、責務の分離
- 日本語コメント・JSDoc の付与
- 各ステップ後に `pnpm test` を実行し、緑を維持していることを確認する

### 5. ④ 検証

以下を**すべて**通す。1つでも失敗したら修正する。

```bash
pnpm lint
pnpm typecheck
pnpm test
```

`src/app/**` のページを追加・変更した場合、または日時・リクエストに依存する値を扱う場合は
**`pnpm build` も実行**し、Route 一覧を確認する。

```bash
pnpm build
```

- 日付や現在時刻で表示が変わるページが `○ (Static)` になっていないか見る。
  静的化されているとビルド時刻が HTML に焼き込まれ、日が変わっても表示が更新されない
- 意図せず静的化されていたら `export const dynamic = 'force-dynamic'` などで明示的に制御する
- **この種の不具合は lint / typecheck / test では検出できない**

### 6. 報告

- 作成・変更したファイルの一覧
- 設計から逸脱した点があれば、その内容と理由（＋設計書の更新提案）
- 検証結果（実行した各コマンドの結果）

## 完了後

`design-impl-reviewer` サブエージェント（設計と実装の突合レビュー）の起動をユーザーに提案する。
レビュー結果の「ワークフロー改善提案」は `docs/ai-feedback.md` に日付付きで追記すること。

その後、`/create-pr` で PR を作成できることも案内する。

## 注意

- Go バックエンドは存在しない。API はモックで実装する
- `console.log` を使わない（`console.warn` / `console.error` のみ）
- `any` を使わない
- 指示なしに `git commit` / `git push` しない
